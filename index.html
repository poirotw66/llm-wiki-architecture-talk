S14Decision boundary · complexity meter

什麼時候普通 RAG 夠，什麼時候需要 LLM Wiki？

FAQMulti-sourceVersionsPartial supersessionGovernance
Ordinary RAG單一權威來源 · 更新慢 · scope 單純
Knowledge Compilation多版本 · ACL · provenance · regression · rollback
不要重造所有 RAG只在 knowledge lifecycle 變複雜時，加上 compilation layer。

複雜度不是消失，而是被搬到更可治理的位置。

WeKnora 等外部知識基礎設施也出現 Wiki、revision、RBAC、audit 等 lifecycle 能力；此處僅作趨勢佐證。整合邊界。

講者稿 · 2:00

這頁回答何時不該做。少量 FAQ、單一權威文件、低更新頻率時，普通 RAG 更簡單。只有當來源變多、版本會部分取代、ACL 與 provenance 變重要、更新需要 release / rollback 時，Knowledge Compilation 才開始划算。Teams Agent 本機文件描述 workflow 與知識問答邊界；外部 WeKnora 只作為 ecosystem 趨勢，不是本案例驗收。

來源：整合邊界。

S15Close · retrieve → compile → release

三句帶走

01RETRIEVE

Not every RAG failure is a retrieval failure.

→
02COMPILE

Move reusable knowledge integration to update time.

→
03RELEASE

Treat enterprise knowledge like a releaseable software artifact.

企業知識，不只是內容。它也需要編譯、測試、版本與發布。

講者稿 · 1:00

第一，找回來源後仍可能判錯適用範圍。第二，將會重複使用的來源整合前移到可審查的更新流程。第三，像軟體一樣保存版本、測試與回滾。DEMO-455 是合成推演；Teams Agent VPN 是待執行的回歸契約；lint fixture 是實際工具紀錄。這些都還不能證明 Wiki 提高了回答準確率。
