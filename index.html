We kept improving retrieval. The unresolved work was knowledge resolution.

本場的問題：知識整合，應該發生在 Query Time，還是 Update Time？

講者稿：今天不是再教一套 RAG pipeline，而是討論企業知識問答裡常被忽略的問題：多份來源都正確，但適用範圍不同時，Agent 要怎麼回答？

S02Hard Case

一個 VPN 問題，四個都「正確」的答案

「我是台南分公司的正式員工，今天換了一台公司管理的新筆電。登入 ExampleVPN 時出現 DEMO-455，該怎麼處理？」

來源看起來正確的答案
A Legacy Guide檢查帳密 + OTP
B Zero Trust Policy分公司正式員工 + managed device 改用 Entra ID + CA
C Service Desk FAQDEMO-455 常見是密碼錯誤
D Incident Postmortem新筆電常是 device compliance 未完成

問題不是找不到文件

RAG 可能把四份都找回來，而且全部都有來源。真正困難的是判斷：哪一份適用於這個人的情境？

Source-grounded 不等於 context-correct。

這能讓 Agent 比單輪 RAG 聰明，但仍把許多知識判斷留在查詢當下。

S04Failure Split

Retrieval 成功，為什麼 Answer 還會錯？

Retrieval problemKnowledge resolution problem
找不到文件找到四份，但適用範圍不同
排序錯新文件只部分取代舊文件
Query 改寫不足FAQ 與 postmortem 同時正確但 scope 不同
Chunk 太小每個 claim 需要自己的 provenance

Reranker 可以改善左邊，但不會自動解決右邊。

S05Core Diagram 1

Query-time integration 才是真正瓶頸

Raw DocumentsA/B/C/D 都在資料庫裡
Retrieval每次找回相關片段
LLM Synthesis臨場判斷適用範圍、衝突、取代關係
Answer如果 scope 判斷錯，答案仍錯

這種架構讓模型每次 query 都重新解一次知識迷宮。

S06Core Diagram 2

把 Knowledge Work 搬到 Update Time

Raw Docs來源進來
Knowledge Compilation整合 scope、衝突、取代關係
Review / Validation結構、語義、回歸問題
Published Knowledge可版本化、可引用、可維護
AgentQuery time 專注於使用者 context 與 workflow

LLM Wiki = Knowledge Contract for Agents. Markdown 只是載體。

S07Evidence

Hard Case：四份互相交疊的 VPN 文件

Source A / Legacy Guide

Legacy VPN 使用帳密 + OTP。DEMO-455 常見是 credential validation failure。

Source B / Zero Trust Policy

分公司正式員工 + managed device 轉 Zero Trust。總公司與 contractor 暫留 Legacy VPN。

Source C / FAQ

DEMO-455 常見是密碼錯誤，但 FAQ 寫於 Zero Trust 遷移前。

Source D / Postmortem

分公司新筆電 DEMO-455 多半是 device compliance 尚未完成。

四份都不是垃圾文件，真正問題是 context-dependent truth。

S11Architecture

Draft → Validate → Knowledge Release

Impact Discovery找候選頁與受影響 query
Mutation PlanCREATE / UPDATE / KEEP / FLAG
Draft Release一批知識變更，而非零散改頁
Validationstructural + semantic + regression queries
Atomic PublishACTIVE pointer N → N+1

失敗時 N 保持 active，不留下半套更新。

S12Evidence Boundary

Structural Valid ≠ Semantic Correct

Structural lint 能抓

missing-summary-v2：缺 source summary、斷鏈，lint exit 1。

Structural lint 抓不到

stale-v2：結構有效，lint exit 0，但下游 query 仍是舊答案。

結構檢查必要，但不能單獨保證知識仍符合最新來源。

S13Integration

LLM Wiki 只是 Knowledge Layer：Teams Agent

Teams企業入口
Intent / IssueIT / Non-IT、問題拆解
FAQ / Knowledge使用 published knowledge
Clarification缺 context 先追問

Knowledge tells the Agent what is true. Business workflow tells the Agent what to do.

S14Decision Framework

WeKnora 與何時值得採用

不值得

少量 FAQ、單一 authoritative source、低更新頻率、無跨文件衝突。

開始值得

大量文件、頻繁改版、部分取代、多人維護、需要 provenance / ACL / lifecycle。

像 WeKnora 這類開源系統，也正在從 RAG 擴展到 Wiki、Revision、RBAC、Audit 與 Knowledge Management。

Knowledge Engineering 正逐漸成為 Agent 架構裡獨立的一層。

S15Close

三句帶走

  1. Not every RAG failure is a retrieval failure.
  2. LLM Wiki moves knowledge integration from query time to update time.
  3. Treat enterprise knowledge like a releaseable software artifact.

企業知識不只是內容。它也需要編譯、測試、版本與發布。
